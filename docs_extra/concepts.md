## DevOps

⚠️ לא נבדק מול מקור רשמי: כל הסעיף. אין ל-DevOps הגדרה רשמית אחת, וכל מקור מגדיר אותו מעט אחרת.

DevOps הוא שם לגישה שמחברת בין צוותי הפיתוח (Development) לצוותי התפעול (Operations), במטרה לפתח, לבדוק ולהעלות תוכנה לאוויר באופן מהיר, אוטומטי ואמין.
הוא כולל תרבות עבודה, תהליכים וכלים, כמו CI/CD, קונטיינרים ואוטומציה של תשתיות.

## CI/CD

CI/CD היא אוטומציה של תהליכי בנייה, בדיקה ופריסה של קוד. GitHub Actions הוא דוגמה לכלי CI/CD.

מקור: https://docs.github.com/articles/getting-started-with-github-actions

⚠️ לא נבדק מול מקור רשמי: הפירוט הבא.

- **CI - Continuous Integration (אינטגרציה רציפה)**: מיזוג שינויי קוד באופן תדיר, כשכל שינוי נבנה ונבדק אוטומטית.
- **CD** משמש לשתי משמעויות שונות:
  - **Continuous Delivery (מסירה רציפה)**: הקוד מוכן תמיד לפריסה, אבל ההעלאה לסביבת הייצור (production) דורשת אישור ידני.
  - **Continuous Deployment (פריסה רציפה)**: כל שינוי שעבר את הבדיקות עולה לסביבת הייצור אוטומטית, בלי אישור ידני.

## GitHub Actions

GitHub Actions היא פלטפורמה של GitHub להרצה אוטומטית של תהליכי בנייה, בדיקה ופריסה.

### רכיבי GitHub Actions

- **Workflow**: תהליך אוטומטי שמורכב מ-Job אחד או יותר. מוגדר בקובץ YAML בתיקייה `.github/workflows` בריפו.
- **Event**: פעולה בריפו שמפעילה Workflow, למשל push של commit או פתיחת pull request. אפשר גם להפעיל לפי לוח זמנים, דרך API או ידנית.
- **Job**: קבוצת Steps שרצים יחד על אותו Runner. כברירת מחדל Jobs רצים במקביל, ואפשר להגדיר שאחד יחכה לאחר.
- **Step**: יחידה בודדת בתוך Job. מריץ סקריפט או Action. ה-Steps רצים לפי הסדר.
- **Action**: משימה מוכנה לשימוש חוזר, שחוסכת כתיבת קוד חוזר. אפשר לכתוב בעצמך או למצוא ב-GitHub Marketplace.
- **Runner**: השרת שמריץ את ה-Job. כל Runner מריץ Job אחד בכל פעם. GitHub מספקת Runners מוכנים, ואפשר גם להפעיל Runner עצמאי.

מקור: https://docs.github.com/articles/getting-started-with-github-actions

## Docker

Docker היא פלטפורמה פתוחה לפיתוח, שילוח והרצה של אפליקציות. היא מאפשרת להפריד בין האפליקציה לתשתית שעליה היא רצה, על ידי אריזת האפליקציה בתוך קונטיינר.

### Image (אימג')

תבנית לקריאה בלבד שמכילה את ההוראות ליצירת קונטיינר. בדרך כלל אימג' נבנה על בסיס אימג' אחר.

### Container (קונטיינר)

מופע רץ של אימג'. אפשר ליצור, להפעיל, לעצור, להעביר ולמחוק קונטיינר. הוא מוגדר על ידי האימג' שלו ועל ידי ההגדרות שניתנות לו בזמן היצירה.

### Dockerfile

קובץ שמגדיר את השלבים לבניית אימג'. כל הוראה בקובץ יוצרת שכבה (layer) באימג'.

### Registry

שירות שמאחסן אימג'ים. Docker מוריד (pull) אימג'ים מה-Registry ומעלה (push) אימג'ים אליו.
Docker Hub הוא Registry ציבורי, ו-Docker מחפש בו אימג'ים כברירת מחדל.

### Docker Compose

כלי לעבודה עם אפליקציה שמורכבת מכמה קונטיינרים.

מקור: https://docs.docker.com/get-started/docker-overview/

## Kubernetes

Kubernetes היא פלטפורמת קוד פתוח לניהול אפליקציות ושירותים שרצים בקונטיינרים. היא תומכת בהגדרות הצהרתיות (declarative) ובאוטומציה.

מקור: https://kubernetes.io/docs/concepts/overview/

⚠️ לא נבדק מול מקור רשמי: רשימת היכולות הבאה נלקחה ממבנה התפריט של אתר התיעוד, ולא מגוף הטקסט. גם הכינוי K8s.
הכינוי המקובל: K8s. בין היכולות: הרצה וניהול של קונטיינרים, הגדלה אוטומטית (autoscaling), רשת ושירותים, אחסון, ניהול הגדרות וסודות (ConfigMaps, Secrets) והרשאות.

### Pod

⚠️ לא נבדק מול מקור רשמי: כל הסעיף. העמוד הרשמי לבדיקה: https://kubernetes.io/docs/concepts/workloads/pods/

היחידה הקטנה ביותר שאפשר לפרוס ב-Kubernetes. Pod מכיל קונטיינר אחד או יותר, שחולקים ביניהם רשת ואחסון.

### Node

⚠️ לא נבדק מול מקור רשמי: כל הסעיף. העמוד הרשמי לבדיקה: https://kubernetes.io/docs/concepts/architecture/nodes/

מכונה (וירטואלית או פיזית) באשכול (cluster) של Kubernetes, שעליה רצים ה-Pods.

### Deployment

אובייקט שמנהל קבוצת Pods שמריצים אפליקציה, בדרך כלל אפליקציה שלא שומרת מצב (stateless).

מקור: https://kubernetes.io/docs/concepts/workloads/controllers/deployment/

⚠️ לא נבדק מול מקור רשמי: ההמשך.
מגדירים את המצב הרצוי, למשל כמה עותקים ואיזה אימג', ו-Kubernetes דואג שהמצב בפועל יתאים לו. בעדכון גרסה ה-Pods מוחלפים בהדרגה, כדי שהאפליקציה תישאר זמינה.

### Service

אובייקט שחושף אפליקציה שרצה באשכול דרך כתובת קבועה אחת, גם כשהאפליקציה מפוזרת על כמה Pods.

מקור: https://kubernetes.io/docs/concepts/services-networking/service/

⚠️ לא נבדק מול מקור רשמי: ההמשך.
זה נחוץ כי Pods נוצרים ונמחקים, והכתובות שלהם משתנות. ה-Service נותן כתובת יציבה ומחלק את הבקשות בין ה-Pods.

## Helm

Helm הוא מנהל חבילות ל-Kubernetes.

### מושגי Helm

- **Chart**: חבילה של הגדרות Kubernetes ש-Helm מתקין. יוצרים עם `helm create`, בודקים עם `helm lint`, ואורזים עם `helm package`.
- **Repository**: מקום שבו מאחסנים ומשתפים Charts. מנהלים עם `helm repo add`, `helm repo list`, `helm repo update`.
- **Release**: מופע של Chart שרץ באשכול, עם שם שבוחרים. כל התקנה, עדכון (upgrade) או חזרה לאחור (rollback) מעלה את מספר הגרסה (revision) של ה-Release.

מקור: https://helm.sh/docs/intro/using_helm/

## GitOps

GitOps היא שיטה לניהול מערכות לפי ארבעה עקרונות, שמפורטים למטה.

⚠️ לא נבדק מול מקור רשמי: בפועל, המצב הרצוי נשמר בדרך כלל ב-Git, ומכאן השם. העקרונות הרשמיים עצמם מדברים על אחסון עם גרסאות, ולא מחייבים דווקא Git.

### ארבעת עקרונות GitOps (לפי OpenGitOps)

1. **הצהרתי (Declarative)**: המצב הרצוי של המערכת מתואר כ"מה צריך להיות", ולא כרשימת צעדים.
2. **בעל גרסאות ובלתי ניתן לשינוי (Versioned and Immutable)**: המצב הרצוי נשמר עם היסטוריה מלאה, כך שאפשר לחזור לכל גרסה קודמת.
3. **נמשך אוטומטית (Pulled Automatically)**: סוכנים מושכים בעצמם את ההגדרות מהמקור, במקום שידחפו אליהם שינויים.
4. **מתואם ברציפות (Continuously Reconciled)**: סוכנים בודקים כל הזמן את המצב בפועל מול המצב הרצוי, ומתקנים כל סטייה.

מקור: https://opengitops.dev/blog/1.0-announcement

## Argo CD

Argo CD הוא כלי Continuous Delivery ל-Kubernetes שעובד בשיטת GitOps.

### איך Argo CD עובד

- המצב הרצוי של האפליקציה מוגדר בריפו Git. ההגדרות יכולות להיות בקבצי YAML רגילים, ב-Helm, ב-Kustomize ועוד.
- Argo CD רץ בתוך Kubernetes ומשווה כל הזמן בין מה שרץ באשכול בפועל (live state) לבין מה שמוגדר ב-Git (target state).
- כשיש הבדל, האפליקציה מסומנת **OutOfSync**, ו-Argo CD מציג את ההבדלים.
- **Sync**: אפשר לסנכרן ידנית, או להגדיר סנכרון אוטומטי, כך שכל שינוי ב-Git מוחל על הסביבה.
- אפשר לעקוב אחרי branch, tag, או commit מסוים.

מקור: https://argo-cd.readthedocs.io/en/stable/
